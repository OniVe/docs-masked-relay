## Fallback conditions

`unzipPackage` keeps `inspectZip` first, so ZIP64, encryption, duplicate names,
limits and ratio bombs behave exactly as before. The wasm path is tried only
when the scanner is ready and:

- total uncompressed size ≤ 128 MiB (`MAX_CODEC_UNCOMPRESSED`);
- no entry has central flag bit 3 (data descriptor);
- non-ASCII names have the UTF-8 flag (OPC names are ASCII anyway);
- every entry is stored/deflated and not `compressedSize=0` with data;
- the archive has at least one entry.

Any wasm load/compile/instantiate failure, trap, entry-count mismatch, size
mismatch or CRC mismatch returns `null` and retries the unchanged `fflate`
path. Partial wasm output is never returned. If fflate also fails, the existing
`ZipError` is thrown. `zipSync` remains on fflate.

The Rust parser has its own checked bounds and returns error codes instead of
`panic` for malformed input; `panic = "abort"` means any unexpected trap is
caught by the JS wrapper and falls back.

## R21-N4 custom expansion: closed

`expandContainedCustomSpans` no longer scans every PERSON span for every CUSTOM
span. PERSON spans are swept by `end` descending into a prefix-max Fenwick tree
keyed by `start`; a CUSTOM query takes the longest inserted span with
`start <= custom.start`, and every inserted span has `end >= custom.end`.
Longest-wins and first-on-tie are unchanged; the index does not rely on CUSTOM
spans being disjoint. O((P+C) log P), O(P) memory.

`bun tests/perf/custom-expansion.ts` (name-dense 2k/4k/8k, custom term
`Иванов Иван => CLIENT`, `labels={CUSTOM}`):

- indexed expansion (synthetic pairs) 1.4 / 1.9 / 3.8 ms; 16k × 16k stress
  8.1 ms vs 669 ms for the legacy double loop (a rollback fails the budget);
- end-to-end mask 134 / 328 / 1 024 ms.

The 8k mask is above the finding's 500 ms example budget. That example stays
advisory and is only reported. The harness gates the name-dense 8k mask at
`MASK_HARD_BUDGET_MS = 1500` ms (`PERF_MASK_HARD_BUDGET_MS` overrides) and
exits non-zero above it; the R22 run is 1 177 ms, so the hard gate holds.

Coverage gap closed in R25 (fail-closed): the **25 MB name-dense corpus is
rejected instead of measured**. The whole-document PERSON path is superlinear,
so a 25 MB name-dense mask would exceed every budget by a wide margin. The
PERSON detector now counts uppercase tokens across all document units
(`/[\p{Lu}](?:[\p{L}\p{M}'’-]+|\.)/gu`, including lone initials such as `И.И.`)
and fails when the aggregate exceeds the cap, so many small units cannot
bypass it after the
cheap uppercase hint and before `buildPersonIndex`/`findPersonMentions`, and
throws `DensityLimitError` (`TOO_MANY_ENTITIES`) above
`MAX_PERSON_TOKENS = 50 000`. The message is constant: «Файл содержит слишком
много имён или сущностей для обработки. Разбейте его на части.» The error
reaches the popup and the automatic-upload toast as its own code (never
`INTERNAL`); no vault or partial output is saved.

Threshold derivation and measurements (R25, Bun 1.4.2):

- 8k name-dense perf corpus = 8 000 x 3 = 24 000 uppercase tokens, 2.08x below
  the cap; `bun tests/perf/custom-expansion.ts` still passes (8k mask 1 180 ms
  under the 1 500 ms hard gate), and the guard itself costs 2.5 ms at 8k.
- 25 MB Cyrillic name-dense text = 672 060 full names / 2 016 180 uppercase
  tokens (~39 UTF-8 bytes per name line), i.e. 40x the cap; `detectAll` now
  rejects it with `DensityLimitError` instead of running the superlinear path.
- The normal 25 MB perf corpus has 0 uppercase tokens in JSON and 1 334 in XML
  (the `CDATA` markers plus the XML declaration) — ~2.7 % of the cap. The full
  `bun tests/perf/json-xml-25mb.ts` run still passes all cases: 25 MB JSON mask
  1 887 ms, 25 MB XML mask 2 563 ms, single-string 1 812 ms, name-dense JSON
  2k/4k/8k 293/537/966 ms.

The expansion itself is indexed and costs ~5 ms at 8k (old numbers 1.4 / 1.9 /
3.8 ms), so the end-to-end remainder is the PERSON detector plus overlap
resolution, not the custom expansion. That cost is outside R21-N4 and stays
recorded by the harness.

## XML status: accepted/documented (not integrated)

Decision: **do not integrate `quick-xml` in round 22; close as
accepted/documented.** `validateXmlText` stays on `saxes` (production), and
`quick-xml` remains benchmark-only in `wasm/codec-bench`.

The P1 benchmark showed an 83 % win for `quick-xml`, but the production
validator runs `saxes` with `xmlns: true`. `quick-xml` without namespace
resolution can accept an undeclared prefix that saxes rejects, which would be a
security regression for the fail-closed OOXML linter. A fast-accept path needs:

- a `NsReader` parity suite covering undeclared prefixes, duplicate expanded
  names, UTF-16/BOM, DTD/entity handling and malformed tags;
- a fallback to `saxes` for anything the parity suite cannot prove;
- a separate feature scope and review, because it changes the security
  boundary of the OOXML/XML acceptance path.

This is a documented integration risk, not an r22 defect. `scanXml` offsets are
untouched.

## Out of scope / risks

- Browser e2e/Playwright not run (Windows); asset fetch and wasm compilation
  were verified only through the production build and Bun tests.
- ZIP64, encrypted entries and data-descriptor archives intentionally fall back
  to fflate; no new support was added.
- The 128 MiB cap means large OPC packages stay on fflate even though
  `DEFAULT_ZIP_LIMITS` allows up to 512 MiB.
- `codec.wasm` is currently emitted as `assets/background.wasm` because it is
  referenced from the background entry; the name is build-generated.
- XML `quick-xml` is benchmark-only; integration is accepted/documented and
  deferred to a separate feature scope with a namespace-parity suite + fallback
  (risk above, not an r22 defect).
